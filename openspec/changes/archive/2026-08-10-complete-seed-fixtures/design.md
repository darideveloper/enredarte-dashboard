## Context

The project seeds data through two commands (see `docs/django-fixtures.md`): `base_loaddata` (auto-loaded in `start.sh`, holds taxonomies/locations) and `seed_loaddata` (manual, one-time, holds demo content). Today the seed tier covers only `Artist`, `ArtistSocialLink`, `ArtistTranslation`, `Artwork`, `ArtworkTranslation`. Six business tables — `ArtCurator`, `ArtCuratorTranslation`, `Gallery`, `GalleryTranslation`, `ArtworkGallery`, `ArtworkImage` — have no fixture at all, so the corresponding admin modules open empty after a fresh seed run.

The loaders (`core/management/commands/base_loaddata.py`, `seed_loaddata.py`) load files via `sorted(os.listdir(...))` with a fail-soft `try/except`. That alphabetical sort is a trap: once we add a `Gallery.json` (G…) and an `ArtworkGallery.json` (A…), the link fixture would load before its `Gallery` FK exists and the fail-soft loop would silently drop every row. `media/` is gitignored, so `ArtworkImage` needs its files committed outside `media/` and synced at seed time.

## Goals / Non-Goals

**Goals:**
- Every business table is populated after a manual `base_loaddata` + `seed_loaddata` on a fresh DB.
- Seed fixtures are deterministic (explicit PKs, es+en translations, matching the existing convention).
- Load order is guaranteed correct regardless of the loader's alphabetical sort.
- `ArtworkImage` rows reference readable files in local dev.

**Non-Goals:**
- No lifecycle change: `seed_loaddata` stays manual per environment; `base_loaddata` stays auto in `start.sh`.
- No admin/auth seeds (`auth.User`, `auth.Group`, `authtoken.Token`) — tables stay empty by design.
- No changes to the base tier (taxonomies/locations already complete).
- No S3 upload automation for seed images (see Risks).

## Decisions

### 1. Numeric-prefix all seed fixture filenames
Rename existing files and add new ones with zero-padded prefixes so `sorted()` yields dependency order:

```
00_ArtCurator.json        01_ArtCuratorTranslation.json
02_Artist.json            03_ArtistSocialLink.json     04_ArtistTranslation.json
05_Artwork.json           06_Gallery.json              07_GalleryTranslation.json
08_ArtworkGallery.json    09_ArtworkImage.json         10_ArtworkTranslation.json
```

Rationale: the loader already sorts alphabetically; prefixes are the documented pattern in `docs/django-fixtures.md` ("prefix the filenames with a numeric prefix") and need zero loader changes. Translation fixtures follow their parent model; `Gallery` (06) precedes `ArtworkGallery` (08). Base tier needs no prefixes (no cross-file FKs beyond models→translations, which already sort correctly).
Alternative considered: a dependency-aware loader (topological sort / two-pass) — rejected as more code and state than data needs.

### 2. Deterministic seed data
New rows use explicit PKs coordinated across files:
- `00_ArtCurator.json`: 2 curators (PK 1–2), Person fields (`name`, `slug`, `email`, `website`, `is_active`, `sort_order`, timestamps). Explicit `slug` is **required**: `ArtCuratorTranslation` is a plain `TranslationBase` (no `SlugBackfillMixin`), so curator slugs are never auto-generated.
- `01_ArtCuratorTranslation.json`: es+en `bio` per curator.
- `06_Gallery.json`: 2 galleries (PK 1–2) referencing curator PKs via `curator` FK; `logo` left blank. `slug` is optional: `GalleryTranslation` carries `SlugBackfillMixin`, so when `07_GalleryTranslation.json` loads the ES row the gallery slug is auto-backfilled from the ES `name` via `unique_slugify`. Supplying an explicit slug keeps it preserved.
- `07_GalleryTranslation.json`: es+en `name` + `description`.
- `08_ArtworkGallery.json`: ~8 links mixing the 6 seeded artworks (PK 1–6) with the 2 galleries (PK 1–2), each with `sort_order`. `slug` is optional: `ArtworkGallery.save()` auto-generates a random token slug when none is provided; explicit slugs are preserved for determinism.
- `09_ArtworkImage.json`: 1 row per artwork, exactly one `is_primary=True` per artwork, image path `artworks/obra-<n>.jpg` (n = artwork PK; file committed in decision 3). `slug` is optional and auto-generated by `ArtworkImage.save()` like `ArtworkGallery`.

`ArtworkGallery` and `ArtworkImage` inherit `BaseModel`, whose `slug` is now `blank=True` (auto-generated in `save()`), so fixtures only supply `is_active`, `sort_order`, and (optionally) `slug`. Explicit slugs are used for the links/images so rows stay deterministic and re-runnable.

**Slug format consistency note**: the existing `05_Artwork.json` keeps its explicit short slugs (`memoria-silente`), which are preserved because `SlugBackfillMixin` only backfills an empty parent slug. Admin-created artworks instead get composite slugs (`{artist.slug}-{title}`). The seeded slugs stay as authored to keep the fixture deterministic; aligning them with the composite format is out of scope.

### 3. Seed images committed under fixtures, synced through the default storage
Commit 6 small JPG placeholders at `artworks/fixtures/artworks/seed/images/artworks/obra-1.jpg` … `obra-6.jpg` (one per seeded artwork). `seed_loaddata.py` gains a short pre-load loop: for each app's `fixtures/<app>/seed/images/`, walk the files and write each one through the configured default storage via `default_storage.exists()` / `default_storage.save()`, preserving the relative path. Files already present in storage are left untouched, so re-runs are no-ops. Because the write goes through the storage backend, the same code serves local dev (`MEDIA_ROOT`) and S3 prod (bucket upload) — no storage-conditional branch.
Rationale: keeps binaries out of git-ignored `media/`, keeps `seed_loaddata` the single manual entrypoint, no new dependencies (Django's `default_storage` is already the platform), and one code path for both backends.
Alternative considered: `shutil.copytree` into `MEDIA_ROOT` only when storage is `FileSystemStorage` — rejected, it adds a backend branch and leaves S3 prod without image files.
Alternative considered: generate placeholder images with Pillow on the fly — rejected, committing real files is simpler and reviewers can see the actual assets.

### 4. Loader change is additive only
`seed_loaddata.py` keeps its discovery/fail-soft behavior; only the media-sync step is added. `base_loaddata.py` unchanged.

## Risks / Trade-offs

- [S3 storage: seed images must reach the bucket] → Mitigation: images are written through `default_storage.save()`, which uploads to the bucket when `STORAGE_AWS` is enabled, so seed images reach S3 at seed time — no manual upload needed.
- [Renaming fixture files breaks external references] → Mitigation: only `seed_loaddata` (filename-agnostic) and `docs/django-fixtures.md` reference these files; no tests reference seed filenames. Update the docs inventory in the same change.
- [Re-running seeds mutates rows in place] → Django's `loaddata` matches rows by explicit PK and performs an UPDATE when the PK already exists, so a re-run is a silent no-op that leaves row counts unchanged (verified end-to-end: the second `seed_loaddata` run exits cleanly with no errors and identical counts). The fail-soft loop remains a safety net for any unexpected per-fixture failure.
- [Prefix collision with future fixture names] → `00`–`10` leaves headroom; future seed files just take the next free slot.

## Migration Plan

1. Add fixtures + images + loader tweak (no DB migration required — fixture data only).
2. Verify locally: fresh DB → `base_loaddata` → `seed_loaddata` → assert all business tables non-empty; run again → counts unchanged.
3. Run test suite.
4. Update `docs/django-fixtures.md` inventory.

Rollback: revert the change; no schema or data migration touched, so nothing to unwind.

## Open Questions

None — scope, counts, and ordering are settled with the user (seeds manual in prod and dev, admin tables empty).
